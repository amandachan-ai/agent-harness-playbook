Agent Harness Playbook

A provider-neutral pattern for keeping agent instructions small, retrieving knowledge only when needed, packaging repeatable workflows, and verifying session and tool behavior. Developed against a command-line coding agent, but the pattern does not depend on any one vendor.

1. Core principle

Do not put every rule, fact, workflow, and tool into one always-loaded file. Separate them by load behavior and responsibility. This reduces context cost, prevents contradictory copies, and gives each change a clear verification path.
ConcernBest homeWhy
Rules that must never be missedGlobal instructionsThey must be visible on every request, so keep them short.
Verified facts, decisions, and incidentsIndexed memory filesThey should be retrieved when relevant, not sent continuously.
Repeatable multi-step workflowsSkillsThey need triggers, ordered steps, guardrails, and completion criteria.
External capabilitiesTool serversCapability configuration should remain separate from policy and knowledge.
Per-session progress and artifactsSession stateConversation-specific state should not become global memory.

2. Architecture

A launch wrapper may add naming, permissions, and optional tool profiles, but the underlying pattern does not depend on a private wrapper. The CLI host snapshots some configuration at startup, so long-lived sessions may continue using older instructions or skill definitions until restarted.

3. Where information belongs

QuestionDecision
Must this behavior apply in every session?Put one concise rule in global instructions and link to detail.
Is this a triggerable workflow with several steps or decision branches?Create a skill.
Is this a fact, decision, failure lesson, or project state?Write an indexed memory entry.
Is this only a low-frequency runbook whose main value is its trap list?Prefer memory over a permanently advertised skill.
Does this add a capability rather than knowledge?Configure a tool server or local language service.
One source of truth per topic Update the existing entry when new evidence overturns an old conclusion. Parallel summaries drift and force future sessions to guess which one is authoritative.

4. Memory pattern

  1. Search the memory index and skills before creating a new entry.
  2. Choose a category that expresses why the entry exists: reference, feedback, project state, evaluation knowledge, or append-only log.
  3. Keep the body self-contained: conclusion, evidence, date, boundaries, and how to apply it.
  4. Add one concise routing cue to the index.
  5. Verify the new file exists, the index points to it, and the global instruction file did not receive a copied index entry.
  6. When evidence changes, correct the source entry in place and mark the superseded conclusion.

The index should be complete but terse. A missing row makes knowledge undiscoverable; a verbose row turns the index into another large document.

5. Skills and subagents

Use a skill when

The same task recurs, has a recognizable trigger, needs ordered steps or branching judgment, and contains guardrails that must not be reconstructed each time.

Use a subagent when

The work is a bounded, one-off investigation or independent review that benefits from a separate context window.

A skill can still launch a subagent. The skill preserves the durable workflow; the subagent provides an independent execution context for one step.

Keep in the main skill fileMove to references
Trigger and mode routingLong prompt templates
Destructive-operation guardrailsBranch-specific procedures
Checks whose omission would be silentLarge examples and background material
Completion and validation contractRare troubleshooting paths

After changing a skill, restart or reload through the supported CLI mechanism and verify that the runtime sees the new definition.

6. Session-state ritual

A lightweight ritual makes a session self-describing without turning the conversation into project-management overhead:

  1. Capture a short title and the intended final product.
  2. Store the title in session metadata so session lists are searchable.
  3. Append a portable index entry if session history is machine-local.
  4. End each response with a compact Recap.
  5. Extend the title when the main topic changes instead of replacing the earlier topic.
Recap linePurpose
Recap:Stable header.
TitleCurrent session topic.
This turnWork completed in the current response.
NextNext actionable step, or an explicit statement that none remains.
Final ProductDeliverable that defines completion.
Metadata must remain valid Quote values written to YAML and parse-check the file immediately. A successful write is not proof that the next resume will succeed.

7. Tool profiles

Keep the daily tool set small. Add specialized or stateful servers through explicit opt-in profiles.

Profile typeUseTrade-off
DefaultCommon repository, documentation, and work-management tasksAvailable in every session; every added server has recurring cost.
Isolated webPublic browsing and browser automationSupports concurrent sessions but has no signed-in state.
Authenticated webSites that require an existing loginA browser profile may be single-holder and cause contention.
Domain-specificSpecialized engineering, data, or security workLoad only for the task that needs it.
Full diagnosticShort-lived troubleshootingUseful for diagnosis, too expensive and failure-prone as a daily default.

7.1 Recovery rule

Validate a recovery with a real tool call. A successful initialization or reconnect message does not prove the next operation will work.

8. Verification, synchronization, and recovery

AreaVerification principle
InstructionsAssert every mandatory behavior is still present.
LauncherTest argument routing, resume behavior, optional profiles, and removal of retired commands.
Process teardownUse ownership, ancestry, creation time, and a dry run; never kill by process name alone.
SynchronizationCompare content hashes, not only timestamps.
BackupsCreate a before-image and integrity manifest before destructive configuration changes.
SecretsSynchronize placeholders, not secret values; restore secrets from a local protected store.
New machineRestore shared knowledge and tools, then recreate machine-local credentials and state.

9. Failure patterns

FailureLesson
A checker stays green while the system is wrongTest the checker against a known failure before trusting it.
A count looks correct despite missing workVerify successful outputs, exact identifiers, hashes, and independent side effects.
A skill silently disappearsValidate frontmatter syntax and confirm runtime discovery.
A session is logged but cannot be found laterRename session metadata; a separate log alone does not solve retrieval.
A configuration file syncs a credentialRedact before synchronization and keep secret material machine-local.
A long document remains valid-looking after a broken editUse structural assertions for required and forbidden content.
Many sessions multiply stateful tool processesClose unused hosts and keep stateful tools opt-in.
A low-level status hides the real causeInspect the raw record and follow the path to the component that performs the final action.

10. Public adaptation checklist

Before publishing a harness document, remove or generalize:

  • Organization-specific wrappers, server names, tool inventories, and product codenames.
  • Account names, email addresses, machine names, local absolute paths, session identifiers, and environment-specific IDs.
  • Private usage measurements, process counts, cost figures, incident details, and access/permission statements.
  • Repository or work-item identifiers that are not already public.
  • Secret formats, authentication material, and instructions that reveal protected infrastructure.
What is safe to keep General architecture, load-behavior trade-offs, memory/skill placement rules, verification methods, public CLI concepts, and failure-prevention patterns that do not depend on a private environment.
